# BPMN Specification Generation Skill

## Purpose

A skill set that parses BPMN-format XML and generates specifications.
It extracts the process overview, flow descriptions, task details, conditional branching logic, and so on from the BPMN process definition, and generates specifications written in Markdown based on the contents described in the artifacts and memos.
The specifications generated by this skill are also used as input prompts when generating the script development model (JSSP).

## When to Use (Creating Specifications)
When the user makes a request such as the following:
- "Create the specifications for this BPMN"
- "Generate the documentation for this process"
- "Output a description of the flow from this XML"

## When to Use (Creating an Import File for IM-Knowledge)
When the user makes a request such as the following:
- "Convert the specifications in `doc/<BPM process name>-prompt/` into a zip that can be imported into Knowledge"
- "Convert the BPM specifications into the Knowledge format"
- "Create a zip for Knowledge"
- "Make it a zip that can be imported into Knowledge"
- "Convert the specifications into the Knowledge format"


## File Structure of the Generated Specifications
doc                              ... directory
 └─ <BPM process name>-prompt    ... directory
      ├─ specification.md        ... describes the overview and overall picture of the BPM process
      ├─ <BPM process name>.bpmn ... the BPMN file in XML format; a copy of the source bpmn file
      ├─ business-data.md        ... business data definitions (table structure; multiple definitions allowed)
      ├─ to-be-discussed.md      ... describes the items to be discussed
      ├─ supplement.md           ... describes the specification adoption policy and supplementary notes
      ├─ interactive-log.md      ... describes the dialogue history, result reports, etc. (write result reports in this file and do not display them on the console)
      └─ <feature directory>     ... directory that stores the specifications of the features linked to BPM tasks (multiple definitions allowed)
           ├─ <feature name>-screen.md ... screen definition (per feature)
           └─ <feature name>-logic.md  ... logic (per feature)

* The structure of the specifications is as above, but files and directories may be added as necessary.

## Specification Style Guide
- Unified terminology: When explaining BPMN elements (tasks, gateways, events, etc.), use the official terms defined in the BPMN specification.
- Formatting conventions: Separate each section of the specifications with headings, and organize information using bullet lists and tables.
- Use of examples: When explaining complex flows or conditional branches, give concrete examples to make the explanation easy to understand.
- Concise wording: Prioritize readability in the specifications; avoid redundant expressions and convey the key points concisely.
- Gather technical details in the appropriate sections so that they do not disrupt the overall flow.
- The contents of the specifications must be faithful to the structure of the BPMN XML. Reflect the XML elements accurately and avoid misleading expressions.
- The contents of the specifications must cover the information necessary to understand the BPMN process definition. Explain the important flows, tasks, conditional branches, and so on without omissions.
- Summarize the specification adoption policy in `<BPM process name>-prompt/supplement.md`.
- Use the "element name" as the primary key for identifying elements, and prohibit identifying elements by ID alone.
- When an element cannot be readily identified by its name alone, supplement it with the element type, lane name, and the names of the preceding and following elements.
- As a rule, do not put IDs in the body text; use them only when necessary as a parenthetical supplement (e.g. element name (ID: xxx)).

> **Details of prohibited descriptions and wording rules:** See "Output Failure Gate" and "Prohibition and Replacement of Technical Jargon" in `reference/guide-to-be-discussed.md`.

## Procedure for Creating Specifications from BPMN

Perform the work according to the following procedure.

## step.1 Check Existing Specifications
- Display a list of the existing specification directories, and confirm whether the BPMN to be read is a differential reflection into existing specifications or whether new specifications are to be created.
  - If an existing specification directory is selected, reflect the contents of the BPMN into that specification as a difference.
  - If new creation is selected, create the specifications anew.

## step.2 BPMN Syntax and Reference Integrity Validation
- [Mandatory gate] Immediately after reading the BPMN file, perform the validation once exactly as defined in `reference/guide-bpmn-validation.md`, and reflect the results into the specifications. **If it has not been performed or not reflected, you must not proceed to step.3.**

## step.3 Create the Specifications
- Create the specifications in accordance with this skill set.
- **For the process definition key (process id), perform "determination and proposal only" (performing the replacement is prohibited).**
  - `reference/guide-process-definition-key-replacement.md` is authoritative for the interpretation and description format of the determination results.
- **Always follow** `reference/guide-to-be-discussed.md` for the chapter organization, heading numbering, and failure conditions of `to-be-discussed.md`. If there is a violation, treat it as an output failure and re-output after correcting it.
- For `to-be-discussed.md`, check the **"Output Failure Gate"** in `reference/guide-to-be-discussed.md`, and if there are applicable items, correct them before outputting.
