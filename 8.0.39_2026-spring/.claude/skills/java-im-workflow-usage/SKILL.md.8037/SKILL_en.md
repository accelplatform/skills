# IM-Workflow Java Integration Program Generation Support Skill

## Purpose

A skill set for newly generating in Java the batch-like processing of a workflow (action process, arrival process, matter start/end process, branch condition process, processing target user plugin, various listeners) using the **JavaEE development model** (abstract classes under `jp.co.intra_mart.foundation.workflow.plugin.process.*`, and listener interfaces under `jp.co.intra_mart.foundation.workflow.listener.*`) provided by intra-mart Accel Platform's IM-Workflow.

**Screens (application/approval/confirmation screens) are out of scope.** The premise is that IM-Workflow screens currently remain as JSSP (`jssp-im-workflow-usage`). This skill handles only "processing programs" that have no screen.

## Differences from the JSSP Version (Important)

The JSSP version (`jssp-im-workflow-usage`) and the Java version are **two independent execution systems** (script execution / Java class execution) for the same extension point, and the implementation models are fundamentally different. Generating something that superficially resembles the other will not work on an actual machine, so always follow the types and signatures in this document.

| Aspect | JSSP Version | Java Version |
|------|---------|---------|
| Implementation unit | 17 functions (`apply`, `approve`, ...) defined in 1 file | 1 class extends an abstract class and **overrides** the methods for the needed processing timings (unused ones are left with the parent's empty implementation) |
| Return value | Assemble and return an `{resultFlag, message, data}` Object yourself | The method's return value itself (`String` / `boolean` / `void`). **Failure is expressed with an exception (`throw new Exception(...)`)**. There is no structure equivalent to `resultFlag`/`message` |
| Error notification | `result.resultFlag = false; result.message = e.message;` | Let the method's `throws Exception` propagate as-is (the workflow engine catches it and treats it as an error) |
| Registration method | Set the **JSSP file path** (without extension) in the import XML's `plugins[].parameter` | Set the **fully qualified class name (FQCN) of the implementation class** in the import XML's `plugins[].parameter` |
| Placement | `src/main/jssp/src/{feature-name}/workflow/...` | `src/main/java/{basePackage}/{feature-name}/workflow/...` (must be compiled and placed on the classpath of the Java runtime environment) |
| Coding conventions | The full set of jssp-related conventions under `.claude/rules/` | The full set of java-related conventions under `.claude/rules/` (`java-naming.md` / `java-code-style.md` / `java-javadoc.md` / `java-logging.md`) |

**What this skill generates is ultimately only Java source files (`.java`).** For the workflow definition's import XML (the part where the FQCN is set in `plugins[].parameter`), generate it by referring to `base-im-workflow-generator`'s Java-support section ("Registering Java Class Execution (JavaEE Development Model)").

## When to Use

When the user makes a request such as:
- "Create the workflow action process in Java"
- "Implement the arrival process in the JavaEE development model"
- "Add the matter start process as a Java class"
- "Implement the branch condition in Java"
- "Implement the processing target user plugin as a Java class"
- "Add the matter delete listener in Java"

If there is no explicit mention of "in Java," "in the JavaEE development model," etc., and the request is simply "create the workflow action process," **default to the JSSP version (`jssp-im-workflow-usage`)**. Only confirm with the user whether the Java version is appropriate if the project's existing implementation is Java-centric (e.g. a lot of business logic already exists under `src/main/java`).

## Implementation Steps

1. Interview the user for requirements (process type, feature name, business logic content, target package)
2. Refer to the applicable `assets/` template to generate the class
   - **Leave unused methods with the parent class's default implementation** (an empty `return null;` / `return true;` / do nothing). Do not force-fill methods that are not implemented for the action process (e.g. not using `reserve`)
   - Always refer to `reference/parameter-reference.md` for the parameter class fields (do not write `getXxx()` from memory or guesswork)
3. Decide the package and placement path (see "Placement Convention" below)
4. Check compliance with `.claude/rules/java-naming.md` / `java-code-style.md` / `java-javadoc.md`
5. Inform the user that the FQCN of the generated class needs to be set in the import XML's `plugins[].parameter` (see `base-im-workflow-generator`'s Java-support section; this skill does not generate the XML itself)

## Placement Convention

### Base Package

If the project has an existing Java package convention, follow it. If not, following the example in `.claude/rules/java-naming.md` (`jp.co.intra_mart.sample.service`, etc.), use the following as the default. **The default is only a default; if the user explicitly specifies otherwise, that takes priority.**

```
{basePackage}.{feature-name}.workflow.{type}
```

Example: feature name `leave` (leave application), base package `jp.co.intra_mart.sample`

```
jp.co.intra_mart.sample.leave.workflow.action    -> LeaveActionProcess.java
jp.co.intra_mart.sample.leave.workflow.arrive    -> LeaveArriveProcess.java
jp.co.intra_mart.sample.leave.workflow.rule      -> LeaveBranchRule.java
jp.co.intra_mart.sample.leave.workflow.plugin    -> LeaveAuthorityExecListener.java
jp.co.intra_mart.sample.leave.workflow           -> LeaveMatterStartProcess.java
                                                     LeaveMatterEndProcess.java
                                                     LeaveMatterArchiveListener.java
                                                     LeaveActiveMatterDeleteListener.java
```

### File Placement

```
src/main/java/{basePackage path separators}/{feature-name}/workflow/{type}/{ClassName}.java
```

Mapping of `{type}` directories (aligned with the JSSP version's convention for the layout under `workflow/` in `.claude/rules/jssp-file-structure.md`):

| Process | Subdirectory |
|------|----------------|
| Action process | `action/` |
| Arrival process | `arrive/` |
| Branch condition / union condition | `rule/` |
| Processing target user plugin | `plugin/` |
| Matter start/end process, various delete/archive listeners | Directly under (no subdirectory) |

### Class Naming

Follow the PascalCase rules in `.claude/rules/java-naming.md`. Make the suffix correspond to the process type:

| Process | Suffix | Example |
|------|------------|-----|
| Action process | `ActionProcess` | `LeaveActionProcess` |
| Arrival process | `ArriveProcess` | `LeaveArriveProcess` |
| Matter start process | `MatterStartProcess` | `LeaveMatterStartProcess` |
| Matter end process | `MatterEndProcess` | `LeaveMatterEndProcess` |
| Branch condition | `BranchRule` | `LeaveBranchRule` |
| Union condition | `UnionRule` | `LeaveUnionRule` |

## Notes

- **Do not start a DB transaction** within the action process, matter start/end process, or branch condition process programs (same constraint as the JSSP version; the transaction is controlled by the engine side)
- **Do not write unimplemented override methods.** Since the parent abstract class provides an empty implementation (`return null;`, etc.), you do not need to fill in override methods for processing timings you don't use. Only override methods that actually implement business logic
- On failure, throw `throw new Exception("message")` or a more specific exception class. There is no structure equivalent to the JSSP version's `result.resultFlag = false`
- Write exception messages descriptively in Japanese, following the convention in `.claude/rules/java-javadoc.md`
- The matter end process uses **the same class** (extending `MatterEndProcessEventListener`) for both the transactional and non-transactional cases. Which extension point it is registered to is switched on the registration side (import XML)
- Branch condition and union condition also use **the same class** (extending `RuleConditionEventListener`). Which extension point it is registered to is switched on the registration side
- The matter delete listeners (active/completed/archived) implement different interfaces (`IWorkflowActvMatterDeleteListener` / `IWorkflowCplMatterDeleteListener` / `IWorkflowArcMatterDeleteListener`). **Only the archived matter delete listener (`IWorkflowArcMatterDeleteListener`) has a 5-argument `execute`** (with `archiveMonth` appended at the end) — its signature differs from the other two (4 arguments). Implementing it with only 4 arguments results in an "unimplemented abstract method" compile error even with `@Override` present. See `assets/matter-delete-listener.md` for details
- The class is instantiated via the classloader at runtime (equivalent to `Class.newInstance()`). **A no-argument constructor is required** (the implicit default constructor satisfies this even without explicitly writing one, but do not make the constructor `private`)

## Verification After Generation

A dedicated verification script equivalent to the JSSP version's `validate-workflow-code.js` is not yet in place. Check the following manually.

1. Whether the FQCN of the parent class/implemented interface matches what is described in `reference/parameter-reference.md`
2. Whether the signature of the overridden methods (argument types, return type, `throws`) exactly matches the abstract class/interface definition (add `@Override` and let the compiler verify it)
3. Whether it complies with `.claude/rules/java-naming.md` / `java-code-style.md` / `java-javadoc.md`
4. `jssp-code-review` / `jssp-security-check` are JSSP-only and do not apply to this skill's output. If the project separately has a code review/security check skill for Java, use that instead
