# 要探讨事项的说明

生成规格书后，须将需要探讨的事项写入本文件，作为与用户讨论时的材料。

## 主要记载事项
- 分析 BPMN 文件，将不明确的部分记载为要探讨事项。
  - 第 3 章记载从 BPMN 结构（分支条件表达式、定时器、循环回退、开始事件类型等）中直接检测到的不明确点。
  - 需注意，第 4 章、第 5 章并非直接从 BPMN 的内容推导出论点，而是以相关要素（数据对象、消息事件、泳道、错误边界事件等）的有无为触发条件，询问作为系统层面需要确认的固定论点的章节。若相关要素不存在，则无需勉强创造论点，可记载为「不适用」。
- 若读取的 BPMN 文件内容中存在 BPMN 本身的错误，须作为指出事项记载。此外，若存在 BPMN 上的改进方案，也须作为提案记载。
- 在进行主数据参照时，若其内容不明确（主数据的定义位置、数据维护的负责人或周期、方法等），须记载到要探讨事项中。
- 若 BPM 上存在独立的任务（未与序列流连接、未配置边界事件），须将其作为可选任务处理，或在「3. 业务需求・运营需求」中记载询问事项。

**注意事项**
- **须确认 BPMN 内 textAnnotation、association、documentation、extensionElements 上的备注描述，并将与需求相关的内容务必反映到要探讨事项中。**
- **问题内容须以非开发者也能理解的平易表达记载，专业术语须进行替换（参见「专业术语的禁止与替换」）。**
- **须务必明确记载「哪个要素存在什么样的问题」。**
- **要素须以要素名称来确定（禁止仅以 ID 单独确定要素。若难以确定，须补充要素种类、泳道名、前后要素名）。**
- **源自备注的论点，须记载「参照要素名（视需要补充 ID）」，以便追溯出处。**
- **若备注内容含糊不清，不得凭猜测确定，须作为「需确认」事项进行论点化。**
- 须以输入的信息（需求备注、目标业务、既有流程上下文）为依据说明不足之处。
- 未确定事项不得断定，须以提问形式保留应确认的论点。

## 要探讨事项（to-be-discussed.md）的结构
- 须按以下优先顺序组织章节。
  1. BPMN 语法・引用完整性验证结果
  2. 流程定义键替换履历
  3. 业务需求・运营需求
  4. 数据・通知・审计
  5. 非功能性・故障应对
  6. BPMN 的改进方案
  7. 注意事项

### 各章的记载内容
1. BPMN 语法・引用完整性验证结果
 - 参见 SKILL.md 的 step.3。
 - 须按照 `.agents/skills/bpm-docs-generator/reference/guide-bpmn-validation.md` 的实施步骤及记载模板进行记载。
 - 若参照的 BPMN 为 iGrafx 制作，须将 `.agents/skills/bpm-docs-generator/reference/guide-specification.md` 「参照的 BPMN 为 iGrafx 制作时必须执行」中的 NG 要素判定结果作为「iGrafx 特有要素兼容性检查」记载（记载规则参见 `.agents/skills/bpm-docs-generator/reference/guide-bpmn-validation.md`）。

2. 流程定义键替换履历
 - 记载 ID 是否已替换、原键/替换后键、重新生成时的复用方针等。
 - 须按照 `.agents/skills/bpm-docs-generator/reference/guide-process-definition-key-replacement.md` 记载。

3. 业务需求・运营需求
 - 记载分支条件定义不足、职责分工不明确、异常处理或终止条件未定义、主数据引用来源不明确等需要业务决策的事项。
 - 关于审批条件、SLA、退回运营、启动方式，须以以下 BPMN 结构上的线索为起点判定不明确点。
   - 审批条件：分支网关的条件表达式（conditionExpression）未定义/为空 → 需确认
   - SLA：是否存在定时器边界事件/定时器中间事件 → 若有设置，须确认期限值的合理性；若没有，须确认是否需要 SLA 本身
   - 退回运营：是否存在返回前一工序的序列流（循环回退）→ 若存在，须确认退回次数上限及负责人变更规则
   - 启动方式：开始事件类型（none/message/timer/signal）→ 若为 none 启动，须确认触发主体
 - 若参照 BPMN 为 iGrafx 制作的 BPMN 且存在调用活动，须记载「调用活动的被调用流程替换履历」。

4. 数据・通知・审计
 - 本章的论点并非直接从 BPMN 的内容推导，而是以以下 BPMN 要素的有无为触发条件，询问系统上需要确认的固定论点。
   - 存在数据对象/数据存储引用 → 须确认保留期限、主数据维护的负责人/周期
   - 存在消息发送任务/消息结束事件 → 须确认通知内容、收件人、是否需要重发、幂等性（是否允许重复发送）
   - 存在涉及审批・驳回・退回等决策的任务 → 须确认审计追踪的必要性及粒度
 - 若不存在上述触发要素，本章可记载为「不适用」。

5. 非功能性・故障应对
 - 本章仅限于记载可从 BPMN 结构中获取线索的论点（权限控制、故障应对）。
 - 记载对象：
   - 权限控制：泳道名、负责人（potentialOwner 等扩展要素）→ 须确认负责角色的合理性、权限范围
   - 故障应对（恢复步骤）：是否存在错误边界事件/升级事件 → 若存在，须具体化恢复步骤；若不存在，须确认是否存在未考虑异常处理的可能性
 - 若上述任一触发条件均不存在，本章可记载为「不适用」。

6. BPMN 的改进方案
 - 针对第 3～5 章，提出改进方案或订正方案等。
   - 第 1 项（源自 validate-bpmn.js 的验证结果，以及 iGrafx 特有要素兼容性检查）因已在 BPMN 语法・引用完整性验证内提出方案，故不包含在本章。
   - 第 2 项因属于 ID 替换方案的提出，故无需提出改进方案。
   - 难以提出方案的课题可以跳过。
 - 改进方案须在明确前提条件与判断依据的基础上，最多提出 3 个方案。

7. 注意事项
 - 记载不属于第 1、3～5 章分类的课题。
   - 第 2 项因属于 ID 替换方案的提出，故无需提出。
   - 第 6 项因属于改进方案，故无需提出。

## 要探讨事项的记述规则

### 专业术语的禁止与替换（必须）
- 以下术语不得在面向非开发者的正文中原样使用。
  - `DI`、`BPMN DI`、`BPMNShape`、`BPMNEdge`、`bpmnElement`、`sourceRef`、`targetRef`、`known set`
- 推荐替换用语：
  - `DI` / `BPMN DI` → 「图形信息（画面上的排布・连接信息）」
  - `BPMNShape` / `BPMNEdge` → 「图中表示的要素・连接线」
  - `bpmnElement` → 「业务流程要素的引用目标」
  - `sourceRef`/`targetRef` → 「连接源/连接目标」

### 输出失败判定（必须）
- 若正文中残留以下任一情形，须将本次输出视为失败，修正后重新输出。
  1. 仅以 ID 单独确定要素（如 `_xx`、`r_xx` 等）
  2. 直接转录原始日志（如「unknown bpmnElement」等）
  3. 未转换的专业术语（`DI`、`BPMNShape`、`BPMNEdge`、`bpmnElement` 等）
  4. 为重要度「低」的事项单独立项
