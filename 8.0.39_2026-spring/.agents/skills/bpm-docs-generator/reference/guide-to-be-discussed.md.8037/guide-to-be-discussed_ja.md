# 要検討事項の説明

仕様書生成後に検討が必要な事項をこのファイルに書き出し、ユーザと議論する際の資料として使用する。

## 主な記載事項
- BPMNファイルを解析し、不明瞭な部分を要検討事項として記載すること。
  - 3章はBPMN構造（分岐条件式・タイマー・ループバック・開始イベント種別等）から直接検出した不明瞭点を記載する章である。
  - 4章・5章はBPMNの内容から論点を直接導出するのではなく、関連要素（データオブジェクト、メッセージイベント、レーン、エラー境界イベント等）の有無をトリガーとして、システムとして確認が必要な定型論点を問い合わせる章であることに留意する。関連要素が存在しない場合、無理に論点を創出せず「該当なし」としてよい。
- 読み込んだBPMNファイルの内容に、BPMN上の誤りがある場合は、指摘事項として記載すること。また、BPMN上の改善案がある場合も、提案として記載すること。
- マスタ参照を行う際、その内容が不明確（マスタの定義先・データメンテナンスの担当やサイクル、方法など）である場合は要検討事項に記載すること。
- BPM上に独立しているタスク（シーケンスフローと結合していない、境界イベントが配置されていない）がある場合、オプショナルタスクとして扱うか「3. 業務要件・運用要件」に問い合わせを記載すること。

**注意事項**
- **BPMN 内の textAnnotation、association、documentation、extensionElements 上のメモ記述を確認し、要件に関係する内容は必ず要検討事項へ反映すること。**
- **問題内容は非開発者にも分かる平易な表現で記載し、専門語は置換する（→「専門語の禁止と置換」参照）。**
- **「どの要素が・どのような問題を抱えているか」を必ず明記する。**
- **要素は要素名で特定する（ID 単独の要素特定は禁止。特定困難な場合は要素種類・レーン名・前後要素名を補足）。**
- **メモ由来の論点は、出典追跡できるように「参照要素名（必要に応じてIDを補足）」を記載すること。**
- **メモの内容が曖昧な場合は推測で確定せず、「要確認」として論点化すること。**
- 入力された情報（要件メモ、対象業務、既存フロー文脈）を根拠として不足点を説明する。
- 未確定事項は断定せず、確認すべき論点を質問形式で残す。

## 要検討事項(to-be-discussed.md)の構成
- 以下の優先順で章立てすること。
  1. BPMN 構文・参照整合性検証結果
  2. プロセス定義キー置換履歴
  3. 業務要件・運用要件
  4. データ・通知・監査
  5. 非機能・障害対応
  6. BPMNの改善案
  7. 留意事項

### 各章の記述内容
1. BPMN 構文・参照整合性検証結果
 - SKILL.mdのstep.3参照
 - `.agents/skills/bpm-docs-generator/reference/guide-bpmn-validation.md` の実施手順・記載テンプレートに従って記載すること。
 - 参照BPMNがiGrafx製の場合、`.agents/skills/bpm-docs-generator/reference/guide-specification.md`「参照BPMNがiGrafx製である場合に必須」のNG要素判定結果を「iGrafx固有要素の互換性チェック」として記載すること（記載ルールは `.agents/skills/bpm-docs-generator/reference/guide-bpmn-validation.md` 参照）。

2. プロセス定義キー置換履歴
 - ID置換済みの有無、元キー/置換後キー、再生成時の再利用方針などを記載する。
 - `.agents/skills/bpm-docs-generator/reference/guide-process-definition-key-replacement.md` に従って記載すること。

3. 業務要件・運用要件
 - 分岐条件の定義不足、責務分担の曖昧さ、例外系や終了条件の未定義、マスタ参照先の不明確、など業務意思決定が必要なものを記載する。
 - 承認条件、SLA、差戻し運用、開始方式については、以下のBPMN構造上の手がかりを起点に不明瞭点を判定する。
   - 承認条件: 分岐ゲートウェイの条件式（conditionExpression）が未定義・空欄 → 要確認
   - SLA: タイマー境界イベント/タイマー中間イベントの有無 → 設定があれば期限値の妥当性、無ければSLA要否自体を要確認
   - 差戻し運用: 前工程へ戻るシーケンスフロー（ループバック）の有無 → 存在する場合、差戻し回数上限・担当変更ルールを要確認
   - 開始方式: 開始イベント種別（none/message/timer/signal） → none開始の場合、トリガー主体を要確認
 - 参照BPMNがiGrafx製BPMNでコールアクティビティがある場合、「コールアクティビティの呼び出しプロセス置換履歴」を記載する。

4. データ・通知・監査
 - 本章の論点はBPMNの内容から直接導出するものではなく、以下のBPMN要素の有無をトリガーとして、システム上確認が必要な定型論点を問い合わせるものである。
   - データオブジェクト/データストア参照がある → 保持期間・マスタ整備の担当/サイクルを要確認
   - メッセージ送信タスク/メッセージ終了イベントがある → 通知内容・宛先・再送要否・冪等性（重複送信可否）を要確認
   - 承認・却下・差戻し等の意思決定を伴うタスクがある → 監査証跡の要否・粒度を要確認
 - 上記トリガーとなる要素が存在しない場合、本章は「該当なし」として記載してよい。

5. 非機能・障害対応
 - 本章はBPMN構造から手がかりが取れる論点（権限制御・障害対応）に限定して記載する。
 - 記載対象:
   - 権限制御: レーン名・担当者（potentialOwner等の拡張要素）→ 担当ロールの妥当性・権限範囲を要確認
   - 障害対応（復旧手順）: エラー境界イベント/エスケレーションイベントの有無 → 存在すれば復旧手順の具体化を、存在しなければ例外系未考慮の可能性を要確認
 - 上記いずれのトリガーも存在しない場合、本章は「該当なし」として記載してよい。

6. BPMNの改善案
 - 3～5について、改善案や訂正案などを提案する。
   - 1（validate-bpmn.js由来の検証結果、および iGrafx固有要素の互換性チェック）はBPMN 構文・参照整合性検証内に提案するため含めない。
   - 2はID置換案の提示であるため、改善案の提示不要。
   - 提案が難しい課題はスキップ可能。
 - 改善案は、前提条件と判断根拠を明示したうえで最大3案を提示する。

7. 留意事項
 - 1・3〜5の章分類に当てはまらない課題を記載する。
   - 2はID置換案の提示であるため、提示不要。
   - 6は改善案であるため提示不要。

### 3章～5章用のテンプレート構成
```md
### <セクション名>

#### <種別>: <対象要素名>

- **対象要素**: <要素名>（<要素種類> / <レーン名> / <前後要素名>など） なお、要素に紐づかない場合、空欄や「プロセス全体」と記載も可
- **問題内容**: <検証結果のエラー種別を平易に記載>
- **影響**: <仕様化・実装・運用への影響を観点別に記載>
- **検討内容**: <意思決定に必要な論点を記載>
- **対応方針**: <要件確認、または6章の改善案への誘導>
```

#### 対応方針について
- 機械的な判断が難しい内容のため、基本は要件確認とする。ただ、改善案の提示できるものは6章への誘導を記載（改善案は6章に記載）

#### 3章コールアクティビティの呼び出しプロセス置換履歴の記載テンプレート

#### <コールアクティビティ名> : 呼出し先プロセスの置換履歴

| 項目 | 値 |
|------|-----|
| 呼出し対象プロセス | <プロセス名> または不明 |
| 元の値（プロセス定義キー） | <callActivityタグのcalledElement属性値> |
| 置換後の値（呼び出し先プロセスのプロセス定義キー） | <processDefinitionKey> または不明 |
| 提案日 | <YYYY-MM-DD> |
| 反映日 | <YYYY-MM-DD または 未反映> |

- 置換後の値が確定した場合は、本テーブルへの記載と同じタイミングで `spec-to-bpmn-fixes.json` にも `operation: "replace-callee-process"` として出力する（`.agents/skills/bpm-docs-generator/reference/guide-specification.md` 参照）。置換後の値が不明な間は出力しない。
- 「反映日」は `.agents/skills/bpm-xml-reflector/reference/bpmn-specs-reflector.md` の `reflectFixes()` が反映後に更新する `spec-to-bpmn-fixes.json` の `reflectedDate` と同期させること。

```md
- **対象論点**: <3〜5章のどの項目に対する改善案か>（例: 「3. 業務要件・運用要件」の「承認条件: 差戻し担当者不明」）

```

## 要検討事項の記述ルール

### 専門語の禁止と置換（必須）
- 以下の語を非開発者向け本文でそのまま使用しないこと。
  - `DI`, `BPMN DI`, `BPMNShape`, `BPMNEdge`, `bpmnElement`, `sourceRef`, `targetRef`, `known set`
- 推奨置換語:
  - `DI` / `BPMN DI` → 「図形情報（画面上の配置・接続情報）」
  - `BPMNShape` / `BPMNEdge` → 「図で表した要素・接続線」
  - `bpmnElement` → 「業務フロー要素の参照先」
  - `sourceRef/targetRef` → 「接続元/接続先」

### 出力失敗ゲート（必須）
- 次のいずれかが本文に残っている場合、出力を失敗扱いにして修正後に再出力すること。
  1. ID単独特定（`_xx`, `r_xx` など）
  2. 生ログ転記（`unknown bpmnElement` など）
  3. 未変換の専門語（`DI`, `BPMNShape`, `BPMNEdge`, `bpmnElement` など）
  4. 重要度「低」の個別起票
