# Multiple Config Operations

There are two major patterns where you want to split `import-<artifactId>-config-N.xml` into two or more files. Both share the principle of **leaving the existing config-1.xml untouched and adding a new config**, but the handling of `spec.version` and the output paths differ.

| Pattern | `spec.version` | Output Location | Use Case |
|---|---|---|---|
| **(I) Version upgrade** | Bumped to `1.1.0` etc. from `1.0.0` | New version directory `1.1.0/` (no suffix on material file names) | Diffs to additionally inject into tenants after release: feature additions, schema extensions, etc. |
| **(II) Adding configs within the same version** | Kept (e.g. still `1.0.0`) | Under the same `1.0.0/`, with file names suffixed `-<N>` (e.g. `equip-authz-policy-2.xml`) | When you want to control execution order **at the initial version's first injection**, e.g. applying policies that follow up on resources generated by LogicDesigner routing |

## Common Design Principles

- **Do not touch the existing `import-<artifactId>-config-N.xml`** (modifying it requires re-injection into existing tenants)
- New diffs are added as a **new `import-<artifactId>-config-(N+1).xml`**
- Setup runs `config-1.xml` → `config-2.xml` → ... in order and executes **all** of them (intra-mart Importer spec)
- Therefore the new config should contain **only the diffs** (do not include already-injected content)

## Pattern (I): Version Upgrade Operation

1. **Create a diff spec.json** (e.g. `equip-v110.spec.json`)
   - Specify `"version": "1.1.0"`, `"configNumber": 2`
   - Describe only the elements to add or change (do not include existing roles or authz)
2. **Run the build script**
   ```bash
   node .agents/skills/jssp-tenant-setup-generator/scripts/build-setup-import.js equip-v110.spec.json
   ```
3. **Existing file protection**: If a file already exists at the output destination, the build **stops with an error**
   - Pass the `--force` flag to overwrite intentionally (normally not used)
4. **Result**:
   - `src/main/conf/products/import/basic/<artifactId>/import-<artifactId>-config-2.xml` (new)
   - `src/main/storage/system/products/import/basic/<key>/1.1.0/...` (new, diffs only; **file names have no suffix**)
   - Existing `config-1.xml` and `1.0.0/` are not touched

## Pattern (II): Adding Configs Within the Same Version

When you keep `spec.version` and only increment `configNumber`, a `-<N>` suffix is appended to the base part of output file names (e.g. `equip-authz-policy-2.xml`). This allows multiple configs' materials to coexist under the same `<version>/`.

Main use case: when you want to **control execution order within the initial setup** between LogicDesigner routing and the authz policies that target it. See [logic-import.md](logic-import.md#injection-order-of-authz-policies-for-routing) for details.

## Sample Diff spec.json

```jsonc
{
  "key": "equip",
  "version": "1.1.0",
  "configNumber": 2,                           // <- Set to 2 to avoid affecting existing config-1.xml
  "shortName": "eqp",
  "displayNames": { "ja": "...", "en": "...", "zh_CN": "..." },

  // No touching existing roles; only additions
  "roles": [
    {
      "id": "equip_auditor",
      "name": "equip_auditor",
      "category": "equip",
      "displayNames": { "ja": "監査担当者", "en": "Auditor", "zh_CN": "审计员" }
    }
  ],

  // No touching existing resources; only additions
  "authzResources": [
    {
      "id": "equip-audit-log",
      "uri": "service://equip/audit/log",
      "parentGroup": "equip-http-services",
      "displayNames": { "ja": "監査ログ", "en": "Audit Log", "zh_CN": "审计日志" }
    }
  ],

  // Only authz policies for the new resource
  "authzPolicies": [
    { "resource": "equip-audit-log", "type": "service", "action": "execute",
      "subject": "S(b_m_role:equip_auditor)", "effect": "PERMIT" }
  ]
}
```

## Pattern (I) Notes

- **DDL diffs**: When running ALTER TABLE against existing tables, syntax differs across PostgreSQL/Oracle/SQL Server, so handle it with per-dialect files such as `1.1.0/equip-ddl_postgre.sql`
- **Prevent duplicate injection**: Do not re-list role IDs in config-2.xml that were already injected in config-1.xml (Importer will error or overwrite)
- **Menu groups**: When you want to change menu items already injected, either keep the menu-id and write the menu-items structure as a diff, or consider separate operational handling
