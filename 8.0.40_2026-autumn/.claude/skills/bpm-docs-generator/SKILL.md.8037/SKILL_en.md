# BPMN Specification Generation Skill

## Purpose

A skill set that analyzes XML in BPMN format and generates a specification document.
From a BPMN process definition, it extracts the process overview, flow descriptions, task details, conditional branching logic, etc., and generates a specification document written in Markdown format based on the content found in artifacts and notes.
The specification document generated by this skill is also used as the input prompt when generating the script development model (JSSP).

## When to Use (Creating a Specification Document)
When the user makes a request such as:
- "Create a specification document for this BPMN"
- "Generate documentation for this process"
- "Output a description of the flow from this XML"

## When to Use (Creating an Import File for IM-Knowledge)
When the user makes a request such as:
- "Convert the specification document in `doc/<BPM process name>-prompt/` into a zip that can be imported into Knowledge"
- "Convert the BPM specification document into Knowledge format"
- "Create a zip for Knowledge"
- "Turn it into a zip that can be imported into Knowledge"
- "Convert the specification document into Knowledge format"


## File Structure of the Generated Specification Document
```
doc                           ...  Directory
 └─ <BPM process name>-prompt ...  Directory
      ├─ specification.md     ...  Describes the process overview and overall picture
      ├─ <BPM process name>.bpmn  ...  BPMN file in XML format, a copy of the source bpmn file
      ├─ business-data.md     ...  Business data definitions (table structure; multiple definitions allowed)
      ├─ to-be-discussed.md   ...  Describes items to be discussed
      ├─ spec-to-bpmn-fixes.json ... Machine-readable data for reflecting the content of the specification document back into the BPMN (for use by bpm-xml-reflector; in addition to the error correction proposals from to-be-discussed.md, it also includes business requirement reflections such as role IDs, task colors, process variables, signals, messages, process definition key replacement, call activity callee replacement, etc.)
      ├─ supplement.md        ...  Describes the specification adoption policy and supplementary notes
      ├─ interactive-log.md   ...  Describes the interaction history and result reports (write result reports to this file; do not display them in the console)
      └─ <feature directory>  ...  Directory holding specification documents for features tied to BPM tasks (multiple definitions allowed)
           ├─ <feature name>-screen.md   ...  Screen definition (per feature)
           └─ <feature name>-logic.md    ...  Logic (per feature)
```

  - **The specification document structure is as shown above, but files and directories may be added as needed.**

## Specification Document Style Guide
- Terminology consistency: When describing BPMN elements (tasks, gateways, events, etc.), use the formal terminology defined in the BPMN specification.
- Formatting conventions: Separate each section of the specification document with headings, and organize information using bullet lists and tables.
- Use of examples: For complex flows or conditional branches, provide concrete examples to make the explanation easy to understand.
- Concise expression: Prioritize readability in the specification document, avoid redundant expressions, and convey key points concisely.
- Organize technical details into the appropriate section so they do not interrupt the overall flow.
- The content of the specification document must faithfully reflect the structure of the BPMN XML. Accurately reflect the XML elements and avoid misleading expressions.
- The content of the specification document must cover the information necessary to understand the BPMN process definition. Explain important flows, tasks, and conditional branches without omission.
- Summarize the specification adoption policy in `<BPM process name>-prompt/supplement.md`.
- Element identification must use the "element name" as the primary key; identifying an element by ID alone is prohibited.
- If an element cannot be identified by name alone, supplement it with the element type, lane name, and/or preceding/following element names.
- As a rule, do not put IDs in the main text; use them only when necessary, as a parenthetical supplement (e.g., element name (ID: xxx)).

> **Details on prohibited descriptions and expression rules:** See "Output Failure Gate" and "Prohibition and Replacement of Technical Terms" in `.claude/skills/bpm-docs-generator/reference/guide-to-be-discussed.md`.

## Procedure for Creating a Specification Document from BPMN

Follow the procedure below.

## Step 1: Confirm the Creation Method (User Response Required)
- List existing specification document directories and ask the user whether to apply a diff to an existing one or create a new one.
- **Do not proceed to step 2 or beyond, including directory creation, until the user's response is obtained.**
  - If an existing specification document directory is selected, reflect the content of the BPMN into that specification document as a diff.
  - If new creation is selected, confirm the directory name, then create the specification document from scratch.

## Step 2: Copy the BPMN
- Copy `<BPM process name>.bpmn` under `prompt`.
- **The copy of `<BPM process name>.bpmn` must be performed using `.claude/skills/bpm-docs-generator/scripts/bpmn-transform.js`.**
  - {{ENSURE_CMD}} .claude/skills/bpm-docs-generator/scripts/bpmn-transform.js <source BPMN> <<BPM process name>-prompt/<BPM process name>.bpmn>
- **This conversion removes iGrafx-proprietary namespace elements/attributes such as ixbpmn:/igx:.** Therefore, detection of iGrafx-proprietary elements ("Required when the referenced BPMN is produced by iGrafx" in `reference/guide-specification.md`) must be performed by **directly referencing the source BPMN (the original file before conversion) with the Read tool**, not the converted `<BPM process name>.bpmn`. Do not duplicate the source BPMN; only reference it, and never modify or overwrite its content.
- Since the path to the source BPMN is also referenced in later steps (especially step 4), be sure to record it as a single line in `interactive-log.md` so it is not forgotten (e.g., `Source BPMN: <path to source BPMN>`). Do not duplicate the file itself.


## Step 3: BPMN Syntax/Reference Integrity Validation
- Immediately after reading the copied BPMN file, perform validation once as defined in `.claude/skills/bpm-docs-generator/reference/guide-bpmn-validation.md`, and reflect the results into the specification document. **You must not proceed to step 4 if this has not been performed and reflected.**

## Step 4: Create the Specification Document
- Create the specification document in accordance with this skill set.
- **Detection of iGrafx-proprietary elements** ("Required when the referenced BPMN is produced by iGrafx" in `.claude/skills/bpm-docs-generator/reference/guide-specification.md`) must be judged by directly referencing, with the Read tool, the source BPMN (the original file before conversion) recorded in `interactive-log.md`. The converted `<BPM process name>-prompt/<BPM process name>.bpmn` must not be used for this judgment, since ixbpmn:/igx: elements have already been removed from it. Writing to or modifying the source BPMN is prohibited (reference only).
  - If the source BPMN can no longer be referenced (e.g., it no longer exists or has been moved), reconfirm with the user as an item to be discussed in `to-be-discussed.md`.
  - In addition to recording the judgment result in the process details of `specification.md`, also reflect it at the same time in Section 1 "iGrafx-Specific Element Compatibility Check" (validation result, severity fixed to "High") and Section 6 "BPMN Improvement Proposals" (remediation proposal) of `to-be-discussed.md`. Do not output this to `spec-to-bpmn-fixes.json` (since the fix and re-import operation is performed on the iGrafx side).
- **For the process definition key (process id), only perform "judgment and proposal" (actual replacement is prohibited).**
  - `.claude/skills/bpm-docs-generator/reference/guide-process-definition-key-replacement.md` is authoritative on how to interpret and describe the judgment result.
- **You must follow** `.claude/skills/bpm-docs-generator/reference/guide-to-be-discussed.md` for the section structure, heading numbering, and failure conditions of `to-be-discussed.md`. If there is a violation, treat it as an output failure, fix it, and re-output.
- Before outputting `to-be-discussed.md`, check the **"Output Failure Gate"** in `.claude/skills/bpm-docs-generator/reference/guide-to-be-discussed.md`, and fix any applicable items before outputting.
- **Confirmed items that require reflection into the BPMN (error correction proposals from validate-bpmn.js, role IDs, task colors, process variables, signals, messages, process definition key replacement, call activity callee replacement) must also be output to `spec-to-bpmn-fixes.json` at the same time they are recorded in `to-be-discussed.md`/`specification.md`.** Do not actually reflect them into the BPMN (that is left to `reflectFixes()` of `.claude/skills/bpm-xml-reflector/reference/bpmn-specs-reflector.md`). `.claude/skills/bpm-docs-generator/reference/guide-bpmn-validation.md` is authoritative on the entry structure and naming conventions.

## Step 5: Record the Interaction History
- Record requests made to the prompt and reports of the generation results in `doc/<BPM process name>-prompt/interactive-log.md`. If there is already a record in `interactive-log.md`, append to it.
  - Record the instruction content requested by the user as-is.
  - Record the response to the instruction content as-is.
