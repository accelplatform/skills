# BPM Specification → intra-mart Knowledge zip Conversion Skill

## Overview

Converts the specification documents generated by bpm-docs-generator (under `doc/<BPM process name>-prompt/`) into a zip file (with a `commons/groups/*.json` and `wiki/<contentsId>/...` structure) that can be imported into intra-mart Knowledge.

The input specification is in Markdown format with a directory hierarchy structure, and the output is a set of JSON files and a zip package corresponding to Knowledge's "group / content / wiki page / attachment" model.

## Input

The `doc/<BPM process name>-prompt/` directory. It follows the structure produced by `bpm-docs-generator`:

```
<BPM process name>-prompt/
├─ specification.md           Overall process specification
├─ <BPM process name>.bpmn    Original BPMN file (attachment)
├─ business-data.md           Business data definitions
├─ to-be-discussed.md         To-be-discussed items
├─ supplement.md             Records the specification adoption policy and supplementary notes
├─ interactive-log.md        Records the interaction history, result reports, etc.
└─ <feature directory>/         (multiple)
   ├─ <feature name>-screen.md   Screen definition
   └─ <feature name>-logic.md    Logic definition
```

## Output

`im_knowledge_<YYYYMMDD>_<HHMM>.zip` (the file name is arbitrary).

The directory structure directly under the zip root is as follows:

```
<im_knowledge_xxx>.zip
├─ commons/
│  └─ groups/
│     └─ im_bpm_specifications.json
└─ wiki/
   └─ <contentsId>/
      ├─ <contentsId>.json
      ├─ <rootPageCd>/
      │  ├─ <rootPageCd>.json
      │  └─ attachment/
      │     └─ <fileCd>            ← the body of the attached file, such as the BPMN (no extension)
      ├─ <pageCd>/
      │  └─ <pageCd>.json
      └─ ...(one for each page)
```

- `<contentsId>` … separated by hyphens using half-width alphanumeric characters (kebab-case)
- `<rootPageCd>` / `<pageCd>` / `<fileCd>` … each a unique, 12–15 character, lowercase alphanumeric ID (see [ID Generation Rules](#id-generation-rules))

## Overall Mapping Table

| Input (under `<BPM process name>-prompt/`) | Output (in the zip) | parentWikiPageCd | sortKey | Notes |
|---|---|---|---|---|
| (the process name itself) | `wiki/<contentsId>/<rootPageCd>/<rootPageCd>.json` | `null` | `"0"` | Root page. title = process name |
| `<BPM process name>.bpmn` | `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>` | - | - | Registered as an attachment of the root page |
| `specification.md` | Specification page | rootPageCd | `"1"` | title = 「仕様書」 |
| `business-data.md` | Business data definition page | rootPageCd | `"2"` | title = 「業務データ定義」 |
| `to-be-discussed.md` | To-be-discussed items page | rootPageCd | `"8"` | title = 「要検討事項」 |
| `supplement.md` | Specification adoption policy/supplementary notes page | rootPageCd | `"9"` | title = 「仕様採用方針と補足事項」 |
| `interactive-log.md` | Interaction history page | rootPageCd | `"10"` | title = 「対話履歴」 |
| `<feature directory>/` | Feature folder page | rootPageCd | `"11"` and onward | title = 「[<feature name>]機能」. Body is `# 機能定義\n\n{{child_pages}}` |
| `<feature directory>/<feature name>-screen.md` | Screen definition page | Feature folder pageCd | `"0"` | title = 「[<feature name>]画面定義」 |
| `<feature directory>/<feature name>-logic.md` | Logic definition page | Feature folder pageCd | `"1"` | title = 「[<feature name>]ロジック定義」 |

> **sortKey Numbering Policy**
> - Among the fixed pages directly under the root, the specification (1) and business data (2) are placed in the first half, and the to-be-discussed items (8) and supplementary notes (9) in the second half
> - Feature folders start from 11 onward.
> - Within a feature folder, screen=0 and logic=1 are fixed

## File Specifications

### 1. Group Definition `commons/groups/im_bpm_specifications.json`

Place all BPM specification documents (contents) under the single fixed group "IM-BPM Specifications." When importing other BPM specification documents into the same Knowledge, share this same groupId.

```json
{
  "groupId": "im_bpm_specifications",
  "groupName": "IM-BPM 仕様書",
  "description": "",
  "localizes": {
    "zh_CN": {"groupId":"im_bpm_specifications","locale":"zh_CN","groupName":"IM-BPM 仕様書","description":""},
    "en":    {"groupId":"im_bpm_specifications","locale":"en",   "groupName":"IM-BPM 仕様書","description":""},
    "ja":    {"groupId":"im_bpm_specifications","locale":"ja",   "groupName":"IM-BPM 仕様書","description":""}
  },
  "createUserCd": "tenant",
  "createDate": <epochMillis>,
  "recordUserCd": "tenant",
  "recordDate": <epochMillis>
}
```

- `createDate` / `recordDate` … the Unix epoch time in milliseconds (a 13-digit number) at the time of generation
- `localizes` must always include all 3 locales (zh_CN / en / ja). Even when not supporting multiple languages, the same text may be used for all of them.

### 2. Content Definition `wiki/<contentsId>/<contentsId>.json`

The content-level metadata corresponding to each BPM process.

```json
{
  "contentsId": "<contentsId>",
  "groupId": "im_bpm_specifications",
  "contentsType": "wiki",
  "contentsName": "<BPM process name>",
  "description": null,
  "contents": null,
  "thumbnail": "data:image/png;base64,<base64-encoded data>",
  "tagIds": [],
  "mainPageCd": "<rootPageCd>"
}
```

- `mainPageCd` … the `wikiPageCd` of the root page (required, must reference it accurately)
- `thumbnail` … optional. Embed a data URL of the BPMN thumbnail PNG, base64-encoded. If omitted, use an empty string or a default image, following the sample.
- `tagIds` … an empty array is fine

### 3. Wiki Pages `wiki/<contentsId>/<wikiPageCd>/<wikiPageCd>.json`

The directory name and the JSON file name must exactly match the `wikiPageCd`.

```json
{
  "wikiPageCd": "<wikiPageCd>",
  "title": "<page title>",
  "parentWikiPageCd": "<parent pageCd or null>",
  "sortKey": "<numeric string>",
  "formatType": "MARKDOWN",
  "contents": "<Markdown body>",
  "comment": "",
  "attachmentFileInfo": [
    {
      "fileCd": "<fileCd>",
      "fileName": "<original file name (with extension)>",
      "createDate": <epochMillis>,
      "comment": ""
    }
  ]
}
```

- `parentWikiPageCd` … `null` for the root page only; the `wikiPageCd` of the parent page for all other pages
- `sortKey` … stored as a **string** (e.g., `"1"`). Since numeric sorting is assumed, do not zero-pad it, as in `"01"`.
- `formatType` … always `"MARKDOWN"`
- `attachmentFileInfo` … `[]` (empty array) when there is no attachment

### 4. Attached File `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>`

- The file name is just `<fileCd>`, with **no extension attached**
- The content is the raw binary of the original file as-is (BPMN is UTF-8 / CRLF XML)
- Must exactly match `attachmentFileInfo[].fileCd` in the page JSON

### 5. Convention for the Root Page Body

The `contents` of the root page follows this fixed pattern:

```markdown
# 仕様

{{child_pages}}

# BPMN
{{attachment(<BPMN file name>.bpmn)}}
```

- `{{child_pages}}` … Knowledge automatically expands this into the list of child pages beneath it
- `{{attachment(...)}}` … embeds the attached file within the body text. The name inside the parentheses must match `attachmentFileInfo[].fileName`

### 6. Body of the Feature Folder Page

As a thin folder page for aggregating child pages, use this fixed body:

```markdown
# 機能定義

{{child_pages}}
```

## ID Generation Rules

`wikiPageCd` / `fileCd` must be a unique, 12–15 character, lowercase alphanumeric string (base36-like) within the zip. Sample examples:

- `012ii53f4f4b6c` (14 characters)
- `8i0vb6rdl34z2kc` (15 characters)

Recommended implementation: generate with something like `Math.random().toString(36).slice(2, 16)`, check for duplicates, and then use it. Adopt a human-readable kebab-case for `contentsId`.

## Conversion of Links Within Markdown

Local relative links within the specification Markdown (e.g., `[business-data.md](business-data.md)`) must be replaced with Knowledge's URL format.

### Replacement Rules

| Original link (example) | After replacement |
|---|---|
| `[業務データ](business-data.md)` | `[業務データ](./knowledge/contents/wiki/<contentsId>/業務データ定義)` |
| `[要検討事項](to-be-discussed.md)` | `[要検討事項](./knowledge/contents/wiki/<contentsId>/要検討事項)` |
| `[<feature name>](<feature directory>/)` | `[<feature name>](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5D機能)` |
| `[<feature name>画面](<feature directory>/<feature name>-screen.md)` | `[<feature name>画面](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5D画面定義)` |
| `[<feature name>ロジック](<feature directory>/<feature name>-logic.md)` | `[<feature name>ロジック](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5Dロジック定義)` |

### Conversion Procedure

1. From the link's local path (relative path), look up the corresponding **page title**
2. Replace the trailing element of the path with the "URL-encoded string of the page title"
3. Standardize the URL prefix to either `./knowledge/contents/wiki/<contentsId>/` or `/imart/knowledge/contents/wiki/<contentsId>/` (keep it consistent within the same specification document)

### URL Encoding Conventions

- Half-width `[` → `%5B`, half-width `]` → `%5D`, half-width space → `%20`
- Japanese characters and full-width parentheses (`（` `）`) are left as-is (they do not need to be encoded, as Knowledge routes them correctly)
- Hash fragments (`#section`) are preserved

## Epoch Milliseconds (Timestamps)

- `createDate` / `recordDate` in `commons/groups/*.json`
- `attachmentFileInfo[].createDate` on pages that have a `wiki/.../attachment`

All of these are numeric Unix epoch time values in milliseconds (e.g., `1779423192916`). It is sufficient to fill them in uniformly with the generation time.

## Conversion Procedure (Implementation Flow)

1. **Input validation** … confirm the existence of the required files (`specification.md` / `business-data.md` / `supplement.md` / `to-be-discussed.md` / `*.bpmn`) directly under `doc/<BPM process name>-prompt/`
2. **Metadata extraction**
   - BPM process name … extracted from the leading `# <name> 仕様書` heading of `specification.md`
   - `contentsId` … the English name of the BPM process (kebab-case). It may also be derived from the BPMN file name.
   - The feature name for each feature directory … extracted from the leading header of the `*-screen.md` file underneath it
3. **Page ID numbering** … assign `wikiPageCd` in the order of root / fixed pages / feature folders / screens / logic. The `fileCd` for the BPMN attachment is assigned in the same way.
4. **JSON construction**
   - Generate `commons/groups/im_bpm_specifications.json`
   - Generate `wiki/<contentsId>/<contentsId>.json` (setting the root page's `wikiPageCd` as `mainPageCd`)
   - Generate a wiki page JSON from each Markdown file (see [File Specifications](#file-specifications) §3)
5. **Conversion of the Markdown body**
   - Read the body text of each page and replace the links with Knowledge's URL format (see [Conversion of Links Within Markdown](#conversion-of-links-within-markdown))
   - Line breaks must be `\n`, and properly escaped as a string within the JSON (double quotes, backslashes, etc.)
6. **Placement of the attached file** … copy the BPMN file, as raw binary, to `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>` (no extension)
7. **zip packaging** … compress the above directory structure as-is into a zip. The recommended zip file name is `im_knowledge_<YYYYMMDD>_<HHMM>.zip`

## Output Example (Minimal Configuration Layout)

```
im_knowledge_<YYYYMMDD>_<HHMM>.zip
├─ commons/groups/im_bpm_specifications.json
└─ wiki/<contentsId>/
   ├─ <contentsId>.json                                    (contentsId.json, mainPageCd=<root>)
   ├─ <root>/<root>.json                                   (title=<BPM process name>, parent=null, sortKey="0")
   │     └─ attachment/<bpmnFileCd>                        (binary of <BPMN file name>.bpmn)
   ├─ <pageA>/<pageA>.json                                 (title=仕様書, parent=<root>, sortKey="1")
   ├─ <pageB>/<pageB>.json                                 (title=業務データ定義, parent=<root>, sortKey="2")
   ├─ <pageC>/<pageC>.json                                 (title=要検討事項, parent=<root>, sortKey="8")
   ├─ <pageD>/<pageD>.json                                 (title=仕様採用方針と補足事項, parent=<root>, sortKey="9")
   ├─ <pageE>/<pageE>.json                                 (title=対話履歴, parent=<root>, sortKey="10")
   ├─ <folderF>/<folderF>.json                             (title=[<feature name>]機能, parent=<root>, sortKey="11")
   ├─ <pageF1>/<pageF1>.json                               (title=[<feature name>]画面定義, parent=<folderF>, sortKey="0")
   ├─ <pageF2>/<pageF2>.json                               (title=[<feature name>]ロジック定義, parent=<folderF>, sortKey="1")
   └─ ...(for the number of feature folders. sortKey continues as 11, 12, ...)
```

## Notes

- **Output the JSON as a single line** (the sample zip is already minified). Indentation for readability is unnecessary.
- **The JSON must be UTF-8 without a BOM**. Do not escape Japanese characters — embed them as-is, in raw form (e.g., `"contentsName":"車両管理"`).
- **The JSON file name/directory name must exactly match `wikiPageCd` / `contentsId` / `fileCd`**. A typo will break the associations during the Knowledge-side import.
- **Strictly maintain the consistency of `parentWikiPageCd`**. Referencing a `wikiPageCd` for a parent that does not exist will cause the import to fail.
- **`mainPageCd` must always point to the root page's `wikiPageCd`**
- **Save attached files without an extension**, and preserve the original file name via `attachmentFileInfo[].fileName`
- **The `{{child_pages}}` / `{{attachment(...)}}` placeholders** are standard Knowledge syntax. The `name` inside `{{attachment(name)}}` must exactly match `attachmentFileInfo[].fileName`
- **Do not leave relative links within the Markdown unconverted** (any missed conversions will result in broken links)
- **Make the groupId a fixed value** so that a zip with the same groupId (`im_bpm_specifications`) can be imported multiple times without issue
- **Do not recommend converting BPMN file names to half-width alphanumeric characters**. Knowledge can also handle Japanese file names; it works as long as the name written inside `{{attachment(...)}}` matches `fileName`.
- **Do not include a slash in a page title.**
