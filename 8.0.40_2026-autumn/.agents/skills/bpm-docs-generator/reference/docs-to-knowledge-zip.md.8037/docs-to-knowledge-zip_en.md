# BPM Specifications → intra-mart Knowledge zip Conversion Skill

## Overview

Converts the specifications generated by bpm-docs-generator (under `doc/<BPM process name>-prompt/`) into a zip file that can be imported into intra-mart Knowledge (a `commons/groups/*.json` and `wiki/<contentsId>/...` structure).

The input specifications are in Markdown format with a directory hierarchy, and the output is a set of JSON files and a zip package corresponding to the Knowledge model of "group / contents / wiki page / attachment".

## Input

The `doc/<BPM process name>-prompt/` directory. It follows the structure of the `bpm-docs-generator` output:

```
<BPM process name>-prompt/
├─ specification.md           overall process specification
├─ <BPM process name>.bpmn    the original BPMN file (attachment)
├─ business-data.md           business data definitions
├─ to-be-discussed.md         items to be discussed
├─ supplement.md              describes the specification adoption policy and supplementary notes
├─ interactive-log.md         describes the dialogue history, result reports, etc.
└─ <feature directory>/       (multiple)
   ├─ <feature name>-screen.md  screen definition
   └─ <feature name>-logic.md   logic definition
```

## Output

`im_knowledge_<YYYYMMDD>_<HHMM>.zip` (the file name is arbitrary).

The directory structure directly under the zip is as follows:

```
<im_knowledge_xxx>.zip
├─ commons/
│  └─ groups/
│     └─ im_bpm_specifications.json
└─ wiki/
   └─ <contentsId>/
      ├─ <contentsId>.json
      ├─ <rootPageCd>/
      │  ├─ <rootPageCd>.json
      │  └─ attachment/
      │     └─ <fileCd>            ← the attachment body such as the BPMN (no extension)
      ├─ <pageCd>/
      │  └─ <pageCd>.json
      └─ ... (one per page)
```

- `<contentsId>` … ASCII alphanumerics separated by hyphens (kebab-case)
- `<rootPageCd>` / `<pageCd>` / `<fileCd>` … each a unique 12–15 character lowercase alphanumeric ID (see [ID Generation](#id-generation-rules))

## Overall Mapping Table

| Input (under `<BPM process name>-prompt/`) | Output (inside the zip) | parentWikiPageCd | sortKey | Notes |
|---|---|---|---|---|
| (the process name itself) | `wiki/<contentsId>/<rootPageCd>/<rootPageCd>.json` | `null` | `"0"` | Root page. title = process name |
| `<BPM process name>.bpmn` | `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>` | - | - | Registered as an attachment of the root page |
| `specification.md` | Specification page | rootPageCd | `"1"` | title = "Specification" |
| `business-data.md` | Business data definition page | rootPageCd | `"2"` | title = "Business Data Definition" |
| `to-be-discussed.md` | Items-to-be-discussed page | rootPageCd | `"8"` | title = "Items to Be Discussed" |
| `supplement.md` | Specification adoption policy / supplementary notes page | rootPageCd | `"9"` | title = "Specification Adoption Policy and Supplementary Notes" |
| `interactive-log.md` | Dialogue history page | rootPageCd | `"10"` | title = "Dialogue History" |
| `<feature directory>/` | Feature folder page | rootPageCd | `"11"` and onward | title = "[<feature name>] Feature". The body is `# Feature Definition\n\n{{child_pages}}` |
| `<feature directory>/<feature name>-screen.md` | Screen definition page | feature folder pageCd | `"0"` | title = "[<feature name>] Screen Definition" |
| `<feature directory>/<feature name>-logic.md` | Logic definition page | feature folder pageCd | `"1"` | title = "[<feature name>] Logic Definition" |

> **Numbering policy for sortKey**
> - Among the fixed pages directly under the root, place the specification (1) → business data (2) in the first half, and the items to be discussed (8) and the supplement (9) in the second half
> - Feature folders start from 11.
> - Inside a feature folder, screen = 0 and logic = 1 are fixed

## File Specifications

### 1. Group definition `commons/groups/im_bpm_specifications.json`

Place all BPM specifications (contents) under the single fixed group "IM-BPM Specifications". This groupId is also shared when importing other BPM specifications into the same Knowledge.

```json
{
  "groupId": "im_bpm_specifications",
  "groupName": "IM-BPM Specifications",
  "description": "",
  "localizes": {
    "zh_CN": {"groupId":"im_bpm_specifications","locale":"zh_CN","groupName":"IM-BPM Specifications","description":""},
    "en":    {"groupId":"im_bpm_specifications","locale":"en",   "groupName":"IM-BPM Specifications","description":""},
    "ja":    {"groupId":"im_bpm_specifications","locale":"ja",   "groupName":"IM-BPM Specifications","description":""}
  },
  "createUserCd": "tenant",
  "createDate": <epochMillis>,
  "recordUserCd": "tenant",
  "recordDate": <epochMillis>
}
```

- `createDate` / `recordDate` … the Unix epoch milliseconds of the generation time (a 13-digit number)
- `localizes` must always include all 3 languages (zh_CN / en / ja). The same text may be used even when multilingual support is not provided

### 2. Contents definition `wiki/<contentsId>/<contentsId>.json`

Meta information per contents unit, corresponding to each BPM process.

```json
{
  "contentsId": "<contentsId>",
  "groupId": "im_bpm_specifications",
  "contentsType": "wiki",
  "contentsName": "<BPM process name>",
  "description": null,
  "contents": null,
  "thumbnail": "data:image/png;base64,<base64 encoded>",
  "tagIds": [],
  "mainPageCd": "<rootPageCd>"
}
```

- `mainPageCd` … the `wikiPageCd` of the root page (required; must be an exact reference)
- `thumbnail` … optional. Embed a data URL containing a base64-encoded PNG thumbnail of the BPMN. When omitted, use an empty string or a default image in line with the sample
- `tagIds` … an empty array is fine

### 3. Wiki page `wiki/<contentsId>/<wikiPageCd>/<wikiPageCd>.json`

Make the directory name and the JSON file name match `wikiPageCd` exactly.

```json
{
  "wikiPageCd": "<wikiPageCd>",
  "title": "<page title>",
  "parentWikiPageCd": "<parent pageCd or null>",
  "sortKey": "<numeric string>",
  "formatType": "MARKDOWN",
  "contents": "<Markdown body>",
  "comment": "",
  "attachmentFileInfo": [
    {
      "fileCd": "<fileCd>",
      "fileName": "<original file name (with extension)>",
      "createDate": <epochMillis>,
      "comment": ""
    }
  ]
}
```

- `parentWikiPageCd` … `null` only for the root page; otherwise the `wikiPageCd` of the parent page
- `sortKey` … stored as a **string** (e.g. `"1"`). Since numeric sorting is assumed, do not zero-pad it like `"01"`
- `formatType` … always `"MARKDOWN"`
- `attachmentFileInfo` … `[]` (an empty array) when there is no attachment

### 4. Attachment `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>`

- The file name is only `<fileCd>`; **do not add an extension**
- The content is the binary of the original file as-is (the BPMN is UTF-8 / CRLF XML)
- Make it match `attachmentFileInfo[].fileCd` of the page JSON exactly

### 5. Conventions for the Root Page Body

The `contents` of the root page follows a fixed pattern:

```markdown
# Specification

{{child_pages}}

# BPMN
{{attachment(<BPMN file name>.bpmn)}}
```

- `{{child_pages}}` … Knowledge automatically expands the list of child pages beneath it
- `{{attachment(...)}}` … embeds the attachment in the body. The name inside the parentheses matches `attachmentFileInfo[].fileName`

### 6. Body of a Feature Folder Page

As a thin folder page for aggregating child pages, use the fixed body:

```markdown
# Feature Definition

{{child_pages}}
```

## ID Generation Rules

`wikiPageCd` / `fileCd` must be 12–15 character lowercase alphanumeric strings (base36-like) that are unique within the zip. Actual samples:

- `012ii53f4f4b6c` (14 characters)
- `8i0vb6rdl34z2kc` (15 characters)

Recommended implementation: generate them with something like `Math.random().toString(36).slice(2, 16)`, check for duplicates, and then use them. Use a human-readable kebab-case value for `contentsId`.

## Conversion of Links within the Markdown

Local relative links within the specification Markdown (e.g. `[business-data.md](business-data.md)`) must be replaced with the Knowledge URL format.

### Replacement Rules

| Original link (example) | After replacement |
|---|---|
| `[Business Data](business-data.md)` | `[Business Data](./knowledge/contents/wiki/<contentsId>/Business%20Data%20Definition)` |
| `[Items to Be Discussed](to-be-discussed.md)` | `[Items to Be Discussed](./knowledge/contents/wiki/<contentsId>/Items%20to%20Be%20Discussed)` |
| `[<feature name>](<feature directory>/)` | `[<feature name>](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5D%20Feature)` |
| `[<feature name> screen](<feature directory>/<feature name>-screen.md)` | `[<feature name> screen](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5D%20Screen%20Definition)` |
| `[<feature name> logic](<feature directory>/<feature name>-logic.md)` | `[<feature name> logic](./knowledge/contents/wiki/<contentsId>/%5B<feature name>%5D%20Logic%20Definition)` |

### Conversion Procedure

1. Reverse-look up the corresponding **page title** from the local path (relative path) of the link target
2. Replace the last element of the path with "the URL-encoded page title"
3. Unify the URL prefix as either `./knowledge/contents/wiki/<contentsId>/` or `/imart/knowledge/contents/wiki/<contentsId>/` (keep it consistent within the same specification)

### URL Encoding Conventions

- Half-width `[` → `%5B`, half-width `]` → `%5D`, half-width space → `%20`
- Japanese characters and full-width parentheses (`（` `）`) are left as-is (routing works on the Knowledge side even without encoding)
- Hash fragments (`#section`) are preserved

## Epoch Milliseconds (Timestamps)

- `createDate` / `recordDate` in `commons/groups/*.json`
- `attachmentFileInfo[].createDate` of pages that have `wiki/.../attachment`

These are all Unix epoch milliseconds as numbers (e.g. `1779423192916`). It is sufficient to fill them all in with the same generation time.

## Conversion Procedure (Implementation Flow)

1. **Input validation** … Confirm the existence of the required files directly under `doc/<BPM process name>-prompt/` (`specification.md` / `business-data.md` / `supplement.md` / `to-be-discussed.md` / `*.bpmn`)
2. **Meta information extraction**
   - BPM process name … extract from `# <name> Specification` at the beginning of `specification.md`
   - `contentsId` … the English name of the BPM process (kebab-case). It may be derived from the BPMN file name
   - The feature name of each feature directory … extract from the header at the beginning of the `*-screen.md` beneath it
3. **Page ID assignment** … Assign `wikiPageCd` in the order root / fixed pages / feature folders / screens / logic. Assign the `fileCd` of the BPMN attachment in the same way
4. **JSON construction**
   - Generate `commons/groups/im_bpm_specifications.json`
   - Generate `wiki/<contentsId>/<contentsId>.json` (set the `wikiPageCd` of the root page in `mainPageCd`)
   - Generate the wiki page JSON from each Markdown file ([File Specifications](#file-specifications) §3)
5. **Conversion of the Markdown body**
   - Read the body of each page and replace the links with the Knowledge URL format ([Conversion of Links within the Markdown](#conversion-of-links-within-the-markdown))
   - Line breaks are `\n`, and the content must already be escaped as a string within the JSON (double quotes, backslashes, etc.)
6. **Placing the attachment** … Copy the BPMN file as binary to `wiki/<contentsId>/<rootPageCd>/attachment/<fileCd>` (no extension)
7. **Creating the zip** … Compress the above directory structure as-is into a zip. The recommended zip file name is `im_knowledge_<YYYYMMDD>_<HHMM>.zip`

## Output Example (Minimal Layout)

```
im_knowledge_<YYYYMMDD>_<HHMM>.zip
├─ commons/groups/im_bpm_specifications.json
└─ wiki/<contentsId>/
   ├─ <contentsId>.json                                    (contentsId.json, mainPageCd=<root>)
   ├─ <root>/<root>.json                                   (title=<BPM process name>, parent=null, sortKey="0")
   │     └─ attachment/<bpmnFileCd>                        (the binary of <BPMN file name>.bpmn)
   ├─ <pageA>/<pageA>.json                                 (title=Specification, parent=<root>, sortKey="1")
   ├─ <pageB>/<pageB>.json                                 (title=Business Data Definition, parent=<root>, sortKey="2")
   ├─ <pageC>/<pageC>.json                                 (title=Items to Be Discussed, parent=<root>, sortKey="8")
   ├─ <pageD>/<pageD>.json                                 (title=Supplementary Notes, parent=<root>, sortKey="9")
   ├─ <pageE>/<pageE>.json                                 (title=Dialogue History, parent=<root>, sortKey="10")
   ├─ <folderF>/<folderF>.json                             (title=[<feature name>] Feature, parent=<root>, sortKey="11")
   ├─ <pageF1>/<pageF1>.json                               (title=[<feature name>] Screen Definition, parent=<folderF>, sortKey="0")
   ├─ <pageF2>/<pageF2>.json                               (title=[<feature name>] Logic Definition, parent=<folderF>, sortKey="1")
   └─ ... (one per feature folder; sortKey continues as 11, 12, ...)
```

## Notes

- **Output the JSON on a single line** (the sample zip is minified). Indentation for readability is unnecessary
- **The JSON must be UTF-8 without a BOM**. Embed non-ASCII characters raw without escaping them (`"contentsName":"車両管理"`)
- **Make the JSON file names and directory names match `wikiPageCd` / `contentsId` / `fileCd` exactly**. A typo breaks the relationships during the import on the Knowledge side
- **Strictly maintain the consistency of `parentWikiPageCd`**. Referring to a `wikiPageCd` whose parent does not exist causes the import to fail
- **`mainPageCd` must always point to the `wikiPageCd` of the root page**
- **Save attachments without an extension** and retain the original file name in `attachmentFileInfo[].fileName`
- **The `{{child_pages}}` / `{{attachment(...)}}` placeholders** are standard Knowledge syntax. The `name` in `{{attachment(name)}}` must match `attachmentFileInfo[].fileName` exactly
- **Do not leave relative links in the Markdown** (any missed conversion results in a broken link)
- Use a fixed value for the groupId **so that importing multiple zips with the same groupId (`im_bpm_specifications`) causes no problems**
- **Do not recommend converting BPMN file names to ASCII alphanumerics.** Knowledge can handle non-ASCII file names as well; it works as long as the name written inside `{{attachment(...)}}` matches `fileName`
- **Do not include slashes in page titles.**
