# TSSP Post-Generation Verification Skill

Responsible for quality verification and fixes of code generated by tssp-page-generator.
Execute the following steps **in order from top to bottom**, repeating fixes until the error count reaches 0. However, always follow the "Fix Loop Principle" below.

Verification covers the following two locations. The `.js` / `.html` files in `src/main/jssp/src` are the output of `tssp build`, so do not edit them by hand; resolve findings by fixing the `src/main/tssp/src` side and rebuilding.

| Path | Content |
|---|---|
| `src/main/tssp/src/{feature-name}/` | Source `.ts` / `.html`. Make fixes here |
| `src/main/jssp/src/{feature-name}/` | Output of `tssp build` (`.js` / `.html` / `.js.map`) and 2WaySQL `.sql` files (placed here because `tssp build` does not output `.sql`; fix findings on `.sql` directly in this file) |

---

## Fix Loop Principle (Important — Applies to All Steps)

**The sequential loop of "find one issue → fix it → re-run → find the next issue → fix it → re-run" is prohibited.** Each validation tool reports all detectable issues in a single run. A sequential loop only repeats unnecessary rework and significantly worsens the total time spent on verification.

1. Run the validation command and **enumerate all reported items at once** (do not start fixing after seeing only the first item)
2. Fix **all enumerated items in a single editing pass** (this may span multiple files/locations; do not repeat Edit → run → Edit → run one item at a time)
3. After fixing, **re-run the same validation command exactly once** and confirm it reaches 0 errors / 0 issues
4. Only if items still remain after that re-run (newly surfaced issues or something missed), repeat steps 2–3 one more time. Ideally, complete the cycle in 2 rounds: "initial detection → batch fix → re-verification"

For **the same anti-pattern appearing in multiple locations** (e.g., missing `DbParameter` wrapping in 5 places), don't just fix the locations shown in the validator's output — first use `grep` to find all other occurrences of the same pattern, then fix them all together.

## Steps 1–3: Automated Validation (Run All → Fix All → Re-verify Once)

Treat the source location check / detection of bypassing type checking / `tssp build --dev` / `validate-jssp-code.js` / `validate-ddl.js` (only if applicable) **as a single set — do not loop detect→fix→re-verify for each one individually**. However, since `validate-jssp-code.js` validates the output of `tssp build`, run it after `tssp build`, and only if the build succeeded.

### First Run (Detection Only — Do Not Fix Yet)

First, at the project root, run the source location check, the detection of bypassing type checking (the list of `.d.ts` files and two greps), and `tssp build` (type checking and Rhino lint). Because `tssp build` is placed last, the exit code of this block is the exit code of `tssp build`.

If "does not exist" is output, the source is not in `src/main/tssp/src/{feature-name}/` (grep may output nothing even when the directory does not exist). Stop verification and fix the source location.

`tssp build --dev` is run through the `tssp:dev` script in package.json. Replace `{package-manager}` with the project's package manager (`bun` / `npm` / `pnpm` / `yarn`).

```bash
test -d src/main/tssp/src/{機能名} || echo "src/main/tssp/src/{機能名} does not exist"
find src/main/tssp -name '*.d.ts'
grep -rnE "\bany\b|@ts-(ignore|expect-error|nocheck)|^[[:space:]]*(export[[:space:]]+)?declare[[:space:]]|^[[:space:]]*///[[:space:]]*<reference" src/main/tssp/src/{機能名}/ --include='*.ts'
grep -rlE "^[[:space:]]*(declare[[:space:]]+global|///[[:space:]]*<reference)" src/main/tssp/src --include='*.ts'
{package-manager} run tssp:dev
```

Only if the build succeeded (exit code 0), check that no hand-placed files exist in the output destination, then run `validate-jssp-code.js` against the output (this script reads only `.js` / `.html` / `.sql` and cannot validate `.ts`).

Any file output by the `find` line is not output of `tssp build` but a file placed by hand in `src/main/jssp/src`. If it is a file generated or edited this time, move it to the same relative path under `src/main/tssp/src/{feature-name}/` (rewrite `.js` as `.ts`) and rebuild. Do not move existing files that are not part of this target; report them to the user.

```bash
find src/main/jssp/src/{機能名} \( -name '*.ts' -o -name '*.js' -o -name '*.html' \) | grep -vxF -f .accel/tssp-generated.txt
node .agents/skills/tssp-page-generator/scripts/validate-jssp-code.js src/main/jssp/src/{機能名}/
```

If the build failed (non-zero exit code), the output does not reflect the current `.ts` files (nothing is written when type checking, lint, conversion, or conflict checking before writing fails). In that case, do not run `validate-jssp-code.js` (it would validate the output of the previous build); fix the build findings until it succeeds, and then run it.

Only if DDL was generated, also run the following at the same time (skip if no DDL path was specified):

```bash
node .agents/skills/tssp-page-generator/scripts/validate-ddl.js src/main/storage/system/products/import/basic/{機能名}/{version}/
```

**Collect the output of all the tools that were run before proceeding.** Do not proceed by fixing one tool at a time and then running the next, as in "fix the `validate-jssp-code.js` results, then run the grep for bypassing type checking" (this causes errors to surface later, triggering a re-loop just for that).

**Note:** `validate-jssp-code.js` / `validate-ddl.js` each accept only a single path (a directory or a single file) per invocation. If you need to validate multiple files together, don't list individual files — pass their common parent directory instead (passing multiple paths causes the script to stop with an error).

### Detected Patterns: validate-jssp-code.js (Build Output Validation)

- `db.select()` / `db.execute()` parameters not wrapped with `DbParameter`
- Strings passed to `DbParameter.number()` (missing `Number()` conversion)
- Use of `var` (use `let` instead)
- `imds-selectbox` (non-existent class name; correct is `imds-select`)
- `imuiCalendar` altField referencing a hidden input
- imart tag `value` attribute enclosed in quotes
- Loading common modules with `include('**/common/**')` (correct is `load()`)
- `load('**/*.js')` calls with `.js` extension (extension is auto-added, resulting in `.js.js` and FileNotFoundException)
- Not receiving the return value of `Transaction.begin(...)`
- TIMESTAMP/DATE column bindings using datetime-like variable names such as `DbParameter.string(startAt|endAt|rangeFrom|rangeTo|...)` (causes type cast error in PostgreSQL)

> **If JSSP-JS-022 warning appears:** Open the corresponding SQL file and confirm whether the parameter is wrapped in `/*IF param != null*/.../*END*/`. If wrapped → false positive (note "SQL-side /*IF*/ guard confirmed" in summary). If not wrapped → fix to empty string fallback like `DbParameter.string(x || '')`.

> **If JSSP-JS-027 / JSSP-JS-028 warnings appear:** Don't stop at rewriting `DbParameter.string(x)` to `DbParameter.timestamp(new Date(x))` or `DbParameter.date(new Date(x))`. `new Date(string)` is unstable to parse in Rhino and will newly trigger `JSSP-JS-016`, adding an extra round. **Fix directly to the final form from the start**, converting to `Date` with `parseLocalDateTime()` (see `post-generation-verification.md` section 3-8 for the helper implementation; add it to the file if not already defined). The return value of this helper is `Date | null` and the argument of `DbParameter.timestamp()` / `DbParameter.date()` is `Date`, so passing it directly as `DbParameter.timestamp(parseLocalDateTime(x))` makes `tssp build` stop with TS2345. Receive it with `let d = parseLocalDateTime(x);` and write `d !== null ? DbParameter.timestamp(d) : new DbParameter(null, DbParameter.TYPE_TIMESTAMP)` (for a DATE column, `DbParameter.date(d)` and `DbParameter.TYPE_DATE`). For a parameter that branches with `/*IF*/` on the SQL side, pass a bare `null` instead of `new DbParameter(null, ...)` (see "[Important] Pass a bare `null` for DATE / TIMESTAMP parameters that branch with `/*IF*/`" in `.agents/requirements/jssp-2way-sql/AGENTS.md`). Since these two rules rely on variable-name heuristics, follow the **same anti-pattern in multiple locations** principle: use `grep` to find all other places passing datetime-like variables to `DbParameter.string(` at once, then fix them all together to the final form.

> **How to fix findings on build output:** The `file:line` in a finding is a position in the output `.js` and its lines are offset from the `.ts`. Search the `.ts` files in `src/main/tssp/src` by the code fragment in the finding (function name, variable name), fix it there, and rebuild. For findings on `.html`, also fix the `.html` on the `src/main/tssp/src` side. Only for findings on `.sql`, fix the file in `src/main/jssp/src` directly.

> **If code that is not written in the `.ts` is flagged:** `var` (`JSSP-JS-002`) and `includes()` (`JSSP-JS-009`) come from temporary variables and helper functions that tssp inserts into the output when converting `?.` / `??` and object spread / rest. Remove those constructs from the `.ts` and write with explicit `null` comparisons and property assignment. Arrow functions (`JSSP-JS-007`) and template literals (`JSSP-JS-012`) are output as written in the `.ts`, so rewrite them with `function` and `+` concatenation. Passing an object literal directly, as in `$data = JSON.stringify({ ... })`, is formatted across multiple lines in the output and results in `JSSP-JS-020`, so put it in a variable first and write `$data = JSON.stringify(<variable>).replace(/\//g, '\\/');` on a single line.

### Detected Patterns: tssp build (Type Checking and Rhino Lint)

`tssp build` checks all `.ts` files under `src/main/tssp/src` in the order type checking → Rhino lint. If there are type errors, lint is not run, so lint violations may appear for the first time in the rebuild after fixing the type errors. This additional round is expected and corresponds to item 4 of the "Fix Loop Principle".

- Type mismatch such as `result.data === 0` (updated count is `result.countRow`)
- Access to methods, properties, or globals not present in d.ts (TS2339 / TS2304, etc.). Read the d.ts and fix to the correct name and signature
- `Request` has an index signature (`[key: string]: Request.Attribute`; `Request.Attribute` is `any`), so `tssp build` passes even when a method not in the d.ts, such as `request.getParamValue()`, is called. List the calls with `grep -rnoE "request\.[A-Za-z_]+\(" src/main/tssp/src/{feature-name}/ --include='*.ts'` and confirm that each method name exists in `d.ts/platform/standard/im-ssjs-request.d.ts`
- Parameters without type annotations (TS7006), and referencing `e` in `catch (e)` without specifying a type (TS18046; write `(e as Error).message`)
- Constructs that cause a syntax error or change meaning in Rhino 1.7.15.1 (`error rhino(no-default-param)`, etc.). For the alternative for each rule, see "Rhino Constraints" in the `tssp-usage` skill
- Output destination conflicts (a file not in `.accel/tssp-generated.txt` exists at the output destination). For how to fix, see "Conflicts" in the `tssp-usage` skill

If the build fails because of a `.ts` outside the target feature, do not fix that file; report it to the user.

### Detected Patterns: Bypassing Type Checking (List of `.d.ts` Files and grep)

Even if `tssp build` succeeds, fix every hit from the list of `.d.ts` files and the two greps as an error. If there are no hits, nothing is output (the exit code of grep is 1). Exclude matches in non-code places, such as the English word "any" in comments or string literals, as false positives.

| Hit | How to fix |
|---|---|
| `any` (`: any`, `as any`, `any[]`, `Record<string, any>`, etc.) | Write the type with a d.ts type or a custom `interface`. Receive values whose type cannot be determined as `unknown`, and narrow them with `typeof` etc. before use |
| `@ts-ignore` / `@ts-expect-error` / `@ts-nocheck` | Delete it, and fix the type error that was hidden to match the d.ts signature |
| Files shown in the list of `.d.ts` files, and `declare` at the start of a line | Delete it. An `interface` in a `.d.ts` can add declarations to d.ts classes or globals even without `declare`, but they do not exist at runtime. To share a type, write `export interface` in a `.ts` and read it with `import type`. Refer to the names of common modules loaded with `load()` through `import` (see `post-generation-verification.md` 3-4). Do not use APIs that are not in the d.ts; report them to the user. Do not fix a `.d.ts` outside the target feature; report it to the user. Adding a `.d.ts` other than `d.ts/` to `include` in `tsconfig.json` at the root or in `src/main/tssp/` is the same kind of bypass, and it does not appear in `find`. Do not fix that `tsconfig.json`; report it to the user |
| `/// <reference` at the start of a line | Delete it. `/// <reference path="..." />` also brings `.d.ts` files outside `src/main/tssp` (places that `find` does not cover) into type checking, which is the same bypass as placing a `.d.ts` |
| A `.ts` outside the target feature shown by the second grep (`declare global`) | Do not fix it; report it to the user. `declare global` also affects type checking of `.ts` files outside the file that declares it, so it bypasses the type checking of the target feature as well. A `declare global` in a `.ts` of the target feature also appears in the first grep, so delete it just like `declare` at the start of a line |

### Detected Patterns: validate-ddl.js (DDL Type Validation, Only If DDL Was Generated)

- PostgreSQL DDL using `NVARCHAR` / `VARCHAR2` / `NUMBER` / `DATETIME2` / `CLOB`
- Oracle DDL using `VARCHAR(` / `NVARCHAR2` / `DECIMAL` / `DATETIME2` / `TEXT` / `BOOLEAN`
- SQLServer DDL using `VARCHAR(` / `VARCHAR2` / `NUMBER` / `TIMESTAMP` / `CLOB` / `TEXT` / `BOOLEAN`
- `CREATE FUNCTION` / `CREATE TRIGGER` / `CREATE PROCEDURE` / `CREATE VIEW` in DDL (causes import failure)
- `CHECK` / `FOREIGN KEY` / `EXCLUDE` constraints defined in CREATE TABLE or ALTER TABLE
- ODBC escapes `{d '...'}` / `{t '...'}` / `{ts '...'}` / `{fn ...}` / `{oj ...}` / `{call ...}` in shared DML file (`*-dml.sql`)

### Batch Fix → Re-verify Once

Following the "Fix Loop Principle," fix all items collected above in a single editing pass (fix the `.ts` / `.html` under `src/main/tssp/src`; only `.sql` is a file under `src/main/jssp/src`), then re-run the same block as the first run (including the source location check and the detection of bypassing type checking (the list of `.d.ts` files and two greps)) **together, exactly once**, in the order `tssp build --dev` → `validate-jssp-code.js` → (if applicable) `validate-ddl.js`, and confirm all reach 0 errors / 0 issues. Only if issues remain, repeat this cycle one more time.

## Step 4: Manual Check

`post-generation-verification.md` is roughly 580 lines long. Reading it in full and cross-checking every category — including ones unrelated to the target screen (DB access, imACMSearch, IM-Workflow, etc.) — can consume nearly half of the total verification time for large screens.
Use the **pre-screening → check only applicable items** procedure below to avoid wasted reading and reasoning.

### Step 4-0: Skip Items Already Covered by Automation

Among the items in `post-generation-verification.md`, any item explicitly marked as "automatically detected by `JSSP-XXX-NNN` in `validate-jssp-code.js`" **does not need to be re-checked if Step 1 (`validate-jssp-code.js`) already came back clean (0 issues)**. The corresponding items are (defer to the doc's own notes if they differ):

| Automated Rule | Corresponding doc Section |
|---|---|
| `JSSP-SQL-001` | 1-2 (Correct use of `/*BEGIN*/`) |

| `JSSP-JS-026` | 3-7 (Unreceived `Transaction.begin` return value) |
| `JSSP-JS-027` | 3-9 (Warning for `DbParameter.string` on datetime-like variable names) |
| `JSSP-HTML-015` | 5-1 (Inline `imdsConfirm` definition) |
| `JSSP-HTML-017` | 4-3 (`window._` bridge) |

Likewise, the "2. tssp build (Type Checking and Rhino Lint)" section is identical to `tssp build --dev` inside "Steps 1–3" of this skill, so **do not re-read or re-run it**.

### Step 4-1: Pre-screen Applicability (grep)

For the remaining items (those without an automated-detection tag), only check them if the target files actually contain the relevant pattern. **Run the following in a single Bash call** and proceed to Step 4-2 only for categories that produced a hit.

```bash
SRC=src/main/tssp/src/{機能名}
OUT=src/main/jssp/src/{機能名}
echo "[SQL files]"; find "$OUT" -name "*.sql" | head -5
echo "[DB access]"; grep -rlE "db\.(select|execute)\(|executeByTemplate|fetchByTemplate" "$SRC" --include='*.ts'
echo "[Date variable parsing]"; grep -rnE "new Date\([a-zA-Z_]" "$SRC" --include='*.ts'
echo "[imACMSearch]"; grep -rl "imACMSearch" "$SRC" --include='*.html'
echo "[Cross-screen parameter passing]"; grep -rlE "location\.href.*\?|<a[^>]+href=\"[^\"]*\?" "$SRC" --include='*.html'
echo "[IM-Workflow]"; find "$SRC" -maxdepth 1 -type d -name workflow
```

For any category with zero hits, note it in the report simply as "Not applicable (confirmed via grep, no matching pattern)" — **do not read the corresponding doc section**.
