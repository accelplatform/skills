# DDL/DML SQL Skeleton Specification

SQL files issued against the database during Sample Data Setup.

The automatic DB-Type suffix (`_postgre` / `_oracle` / `_sqlserver`), the file resolution priority, and the type mapping are identical to Tenant Setup.
See `.claude/skills/jssp-tenant-setup-generator/reference/database-sql.md`.

## Scope

| Material | Target tables | spec |
|---|---|---|
| **DDL** (`<create-file>`) | **Tables used by Sample Data Setup alone** | `tables[].ddl: true` |
| **DML** (`<insert-file>`) | All tables that receive sample data | All entries in `tables[]` |

Tables for the module itself are generated by `jssp-tenant-setup-generator` under `storage/system/products/import/basic/<key>/<version>/`. If you only INSERT into an existing table, do not specify `ddl`.

| Nature of the table | Where to create the DDL |
|---|---|
| Required for the module to run | Tenant Setup (`basic/`) |
| Exclusive to Sample Data Setup | **Sample Data Setup (`sample/`, this skill)** |

## Re-import When the Table Already Exists

**Sample Data Setup runs every time setup is executed.** Because it re-runs while the tables already exist, **a plain `CREATE TABLE` always fails from the second run onward.**

DDL is not transaction-controlled. In addition, the subsequent setup processing continues even when an exception occurs, so **the run does not stop on an error, and you cannot notice the failure without looking at the log.**

### Choosing an Approach

| Approach | Behavior from the second run onward | Existing data | Notes |
|---|---|---|---|
| **CREATE with an existence check** (recommended) | Skipped | Retained | Requires dialect-specific syntax (see the table below). Not available below Oracle 23ai (see the caution below) |
| `DROP` then `CREATE` | Recreated | **Lost** | For when you want to return to the initial state every time. Use `DROP TABLE IF EXISTS` on PostgreSQL / SQL Server. **Not available below Oracle 23ai** (see the caution below) |
| Plain `CREATE TABLE` (no existence check) | The leading `CREATE` raises ORA-00955 or similar, and **the following statements are skipped** | Retained | Harmless if all tables were created on the first run, but errors keep appearing in the log |

To avoid destroying the data users entered during trial use, **"CREATE with an existence check" is recommended as the default**.

### Importer SQL Execution Behavior (Important)

The Importer **splits SQL files mechanically at a semicolon followed by whitespace (`;\s*\n?`)** and executes them one statement at a time. This behavior places strong constraints on how DDL must be written.

- **If even a single statement fails, the entire rest of that file goes unexecuted** (the exception aborts processing of the file immediately). Moreover, a DDL error merely writes a warning log and moves on to the next file, so **the setup itself continues and is treated as a "success"**.
- Therefore, **placing a `DROP` or `CREATE` without an existence check at the top makes the first run fail right there, skipping every remaining CREATE in the same file**. The run ends as a "success" without creating a single table, and all subsequent DML fails.
- Write each statement so that it succeeds on its own (`CREATE TABLE IF NOT EXISTS`, `DROP TABLE IF EXISTS`, etc.).
- The split does not recognize comments. **A `;` inside a comment cuts the statement there, and the comment-only chunk runs as SQL and breaks**. The same applies when a comment is left after the last `;`. **Always delete the comment lines when you write the implementation.**

### Existence Check Syntax per Dialect

| DB | Syntax |
|---|---|
| **PostgreSQL** | `CREATE TABLE IF NOT EXISTS <table> ( ... );` |
| **SQL Server** | `IF NOT EXISTS (SELECT 1 FROM sys.tables WHERE name = '<table>') CREATE TABLE <table> ( ... );` |
| **Oracle** | `CREATE TABLE IF NOT EXISTS` is available **only on 23ai or later**. Earlier versions require a PL/SQL block (see the caution below) |

```sql
-- PostgreSQL
CREATE TABLE IF NOT EXISTS any_app_demo (
    data_id     VARCHAR(64)  NOT NULL,
    tenant_id   VARCHAR(64)  NOT NULL,
    data_name   VARCHAR(256),
    PRIMARY KEY (data_id)
);
```

```sql
-- SQL Server
IF NOT EXISTS (SELECT 1 FROM sys.tables WHERE name = 'any_app_demo')
CREATE TABLE any_app_demo (
    data_id     VARCHAR(64)  NOT NULL,
    tenant_id   VARCHAR(64)  NOT NULL,
    data_name   VARCHAR(256),
    PRIMARY KEY (data_id)
);
```

### Existence Checks Cannot Be Written Below Oracle 23ai

**On Oracle 23ai or later**, `CREATE TABLE IF NOT EXISTS` is available, so write it with an existence check just like the other DBs.

**Below Oracle 23ai**, `CREATE TABLE IF NOT EXISTS` is unavailable and an existence check requires an anonymous PL/SQL block (`BEGIN ... END;`). However, as described above, the Importer does not track PL/SQL and splits mechanically at semicolons, so **it splits at the semicolons inside the block as well; the fragments run as standalone SQL, and the leading `DECLARE ...` already raises ORA-00900 (invalid SQL statement)**. Since PL/SQL cannot be written without semicolons, **this approach is fundamentally unworkable**.

Likewise, the approach of putting `DROP` -> `CREATE` in the same file cannot be used below Oracle 23ai. `DROP TABLE IF EXISTS` is also 23ai or later only, and a plain `DROP` fails with ORA-00942 on the first run because the table does not exist yet -> the rest of the file is skipped -> the table is never created, and **the same state repeats from the second run onward and never recovers** (see "Importer SQL Execution Behavior" above).

**Practical approaches below Oracle 23ai:**

| Approach | Behavior |
|---|---|
| Write **only a plain `CREATE TABLE` in the DDL, without mixing in `DROP`** | Creation succeeds on the first run. From the second run onward the leading `CREATE` stops with ORA-00955 and the rest is skipped, but since every table was created on the first run there is no actual harm. Errors keep appearing in the log |
| Create the tables in an extended import (`doImport`) | If you check existence on the JS side and then issue `CREATE` through `TenantDatabase`, you are not subject to the Importer's SQL splitting constraint ([extends-import.md](extends-import.md)) |

In either case, verify that the tables are reliably created on the first run and that the errors in the second run's log are expected.

## Idempotency of DML

As with DDL, **a simple `INSERT INTO ... VALUES (...)` violates a unique constraint on the second run.**

| Technique | Description | Dialect-dependent |
|---|---|---|
| **`INSERT ... WHERE NOT EXISTS`** | INSERT only when the row does not exist (recommended) | No |
| **`DELETE` then `INSERT`** | A full refresh within the same DML file | No |
| `MERGE` / `ON CONFLICT` / `IF NOT EXISTS` | Requires `dmlPerDialect: true` | **Yes** |
| Full refresh in an extended import | Implemented in `doImport` without using DML ([extends-import.md](extends-import.md)) | No |

```sql
INSERT INTO any_app_data (data_id, tenant_id, data_type)
SELECT 'sample_001', 'default', 'SAMPLE'
WHERE NOT EXISTS (SELECT 1 FROM any_app_data WHERE data_id = 'sample_001');
```

## File Layout

| File | Content |
|---------|------|
| `<key>-ddl_postgre.sql` / `_oracle.sql` / `_sqlserver.sql` | CREATE TABLE statements (always three dialect-specific files) |
| `<key>-dml.sql` | Sample data INSERT statements (shared by all DBs, when `dmlPerDialect: false`) |
| `<key>-dml_postgre.sql` / `_oracle.sql` / `_sqlserver.sql` | Same as above (when `dmlPerDialect: true`) |

> **This is a different file from `<key>_sample-dml.sql` on the Tenant Setup side**. That one is DML that loads **initial data for production operation** and is placed under `basic/<key>/<version>/` (owned by `jssp-tenant-setup-generator`).

References in the config carry no suffix. The order is DDL -> DML:

```xml
<database>
  <create-file>products/import/sample/<key>/<key>-ddl.sql</create-file>
  <insert-file>products/import/sample/<key>/<key>-dml.sql</insert-file>
</database>
```

## Specification in spec.json

```json
"database": {
  "tables": [
    { "name": "any_app_data", "comment": "サンプルデータ" },
    { "name": "any_app_demo", "comment": "デモ用テーブル", "ddl": true }
  ],
  "dmlPerDialect": false
}
```

| Field | Required | Default | Content |
|-----------|------|---------|------|
| `tables[].name` | YES | - | Table name |
| `tables[].comment` | NO | - | Description of the table (expanded into a comment) |
| `tables[].ddl` | NO | `false` | `true` generates a DDL (`CREATE TABLE`) skeleton. **Specify it only for tables exclusive to Sample Data Setup** |
| `dmlPerDialect` | NO | `false` | Whether to output DML as three dialect-specific files |

If no table has `ddl: true`, no DDL file is generated and no `<create-file>` is written to the config.

If `database` is omitted, no SQL file is generated and the `<database>` section is omitted from the config as well.

## Notes

- **Comments inside SQL statements are not supported** (by specification). The build script outputs a skeleton containing comment lines as guidance, so **delete the comment lines once you have written the implementation**
- End each SQL statement with a semicolon `;`
- Limit DML to master-type initial data. **Do not include business transaction data**
- Tables without `ddl` must already be created by the Tenant Setup DDL
- Use UTF-8 (without BOM) for the character encoding, and LF for line breaks (recommended)
- **Verify by running Sample Data Setup twice in a row** ([checklist.md](checklist.md))
